# Roller Derby Platform — Security & Cosmetic Audit

*Audited June 2026. Backend (Node/Express/MySQL) and frontend (React/Vite/SCSS).*

## How to read this

Issues are ranked by severity. Each has: **the file**, **what's wrong**, **why it matters**, and **the exact fix**. Apply them in VS Code one at a time, top to bottom, and re-deploy / re-test after each. Don't batch them — that's how the hard-to-trace breakage happens.

A note before the bad news: **this backend is well-built.** Parameterized SQL everywhere (no injection), bcrypt password hashing, password-strength validation, a real Content-Security-Policy, security headers, `x-powered-by` disabled, login rate-limiting, file-upload size limits, production error-message suppression, and ownership checks on user edit/delete. That is stronger than most junior portfolios. The findings below are a short list against an otherwise solid base — say that in interviews.

## SECURITY

### 🔴 CRITICAL — Privilege escalation via registration

**File:** `backend/controllers/userController.js` (`saveUser`), with `backend/models/UserModel.js` (`saveOneUser`).

**What's wrong.** `saveUser` builds the new user from the entire request body:

```js
const userData = { ...req.body, password: hashedPassword };
await UsersModel.saveOneUser(userData);
```

and `saveOneUser` writes `userData.role || 'user'` into the database. Nothing strips `role` from the incoming body. So anyone hitting `POST /api/v1/register` with:

```json
{ "firstName": "x", "lastName": "x", "email": "a@b.c", "password": "Abcdef12", "role": "admin" }
```

**creates themselves an admin account.** This is the single most serious issue in the codebase — it hands full admin to any anonymous visitor, defeating every `withAuthAdmin` gate elsewhere.

**Why it matters.** Your *update* path is already safe — `UserModel.updateUser` uses a field whitelist that excludes `role`, so users can't escalate by editing their profile. But registration bypasses that whitelist entirely. One hole undoes the otherwise-correct authorization model.

**The fix.** Force the role server-side at registration; never trust the client for it. In `saveUser`, replace the spread with an explicit object that hard-codes the role:

```js
// Build the user explicitly — do NOT spread req.body (it lets clients set `role`).
const userData = {
  firstName: req.body.firstName,
  lastName:  req.body.lastName,
  email:     req.body.email,
  password:  hashedPassword,
  address:   req.body.address,
  zip:       req.body.zip,
  city:      req.body.city,
  phone:     req.body.phone,
  role:      'user', // always 'user' on self-registration; promote admins manually/in DB
};
await UsersModel.saveOneUser(userData);
```

After this, the only way to get an admin is a deliberate one (DB update, or an admin-only endpoint you control). Test: register with `"role":"admin"` in the body and confirm the created account is still a normal user.

### 🟠 HIGH — Self-registration of admins should be impossible by design

**File:** same as above.

This is the same root cause stated as a *principle* worth internalizing, because it generalizes: **the client decides nothing about authorization.** Role, ownership, permissions — all server-side, always. The fix above closes the specific hole; the habit closes the class. Any time you write `{ ...req.body }` into a database, ask "what fields am I accidentally letting the client set?" That question, asked out loud, is also a strong interview signal.

### 🟡 MEDIUM — JWT stored in localStorage (XSS token theft exposure)

**Files:** `frontend/src/features/auth/Login.jsx`, `frontend/src/api/axios.js`, `frontend/src/redux/userSlice.js`, others.

**What's wrong.** The auth token lives in `localStorage`. Any JavaScript that runs on your page can read `localStorage.getItem('token')` and exfiltrate it. If an XSS bug ever lands (a malicious comment, a compromised dependency), the attacker walks away with live sessions.

**Why it's only MEDIUM here, not HIGH.** You currently have *no* obvious XSS vector — no `dangerouslySetInnerHTML`, React escapes content by default. So the exposure is latent, not active. But localStorage tokens are an industry-known tradeoff, and an interviewer may well ask "where do you store your token and what's the risk?" You want to be able to answer it.

**The fix (two options, pick per effort):**

- *Proper fix (more work):* move the token to an **httpOnly cookie** set by the backend at login. httpOnly cookies are unreadable from JavaScript, so XSS can't steal them. This requires backend changes (set-cookie on login, read cookie in `withAuth`) and CSRF protection (since cookies auto-send). It's the "correct" answer but a real refactor.
- *Pragmatic stance (no code):* document that you knowingly use localStorage for simplicity, that you mitigate by having no XSS surface and a strict CSP, and that the migration path is httpOnly cookies. For a portfolio project, a clear-eyed writeup of the tradeoff is often better than a half-done cookie migration. **Don't start the cookie refactor unless you'll finish it** — a half-migrated auth system is worse than a documented localStorage one.

### 🟡 MEDIUM — Stray debug endpoints and console noise

**File:** `backend/server.js`, and 14 `console.log`/`console.warn` calls across the backend.

**What's wrong.** `/api/v1/debug` and `/test-direct` exist (gated behind `NODE_ENV !== 'production'`, which is good), and there are ~14 console statements. The gating means they shouldn't leak in prod, *if* `NODE_ENV` is correctly set on Railway. Two risks: (1) if `NODE_ENV` is ever unset/misconfigured, the debug routes and CORS-origin logging go live; (2) `console.error(err.stack)` in `errorHandler.js` always runs and prints full stack traces to your logs — fine for you, but noisy and a minor info-leak if logs are ever exposed.

**The fix.**
- Confirm `NODE_ENV=production` is set in your Railway environment variables (check the dashboard). This one setting is what makes all the `!== 'production'` guards actually protect you.
- Optionally remove `/test-direct` entirely — it serves no purpose.
- Leave `console.error(err.stack)` for now; it's standard. If you later add a logger (pino/winston), route it through that.

## COSMETIC

The theme system (`_variables.scss`) is good — proper light/dark variable pairs. The problem is **consistency**: several stylesheets bypass the variables with hardcoded colors, so they break when the theme switches (the exact bug we already fixed in `_comments`, `_dashboard`, `_products`). Remaining offenders, by file:

### 🟡 Hardcoded colors still present in 7 SCSS files

**Files:** `_card.scss`, `_cart.scss`, `_dashboard.scss`, `_navbar.scss`, `_orders.scss`, `_products.scss`, `_shop.scss`.

(`_dashboard` and `_products` are mostly fixed already; the greps catch leftover one-offs like `#ffffff` on a single button.)

**What's wrong.** Hardcoded hex values (`#fff`, `#4b5563`, `#e5e7eb`, etc.) don't respond to the theme. In whichever mode they weren't designed for, you get low-contrast or invisible elements — same family as the white-on-white product text.

**The fix (mechanical, low-risk).** In each file, replace hardcoded colors with the variable that matches its role:

| Hardcoded | Replace with | Role |
|---|---|---|
| `#fff` / `#ffffff` (backgrounds) | `var(--card)` | surfaces |
| `#fff` (button text) | `var(--accent-contrast)` | text on colored buttons |
| dark text (`#0b1220`, `#111`, `#1f2937`) | `var(--text)` | primary text |
| grey text (`#6b7280`, `#4b5563`, `#9ca3af`) | `var(--text-muted)` | secondary text |
| borders (`#e5e7eb`, `#d1d5db`, `#ccc`) | `var(--border)` | borders |
| blue accents (`#3b82f6`, `#2563eb`, `#4f46e5`) | `var(--accent)` / `var(--accent-hover)` | accents |
| green (`#10b981`, `#059669`) | `var(--success)` / `var(--success-hover)` | success/CTA |
| red (`#ef4444`, `#b91c1c`) | `var(--danger)` | destructive |
| shadows (`rgba(0,0,0,...)`) | `var(--shadow-1)` / `var(--shadow-2)` | elevation |

Do one file, save, `git add -A <file>`, commit, push, re-test in both themes. Repeat. (Use `git add -A` — plain `git add` silently no-ops on this setup.)

To find every offender in a file: search it for `#` and for `rgba(`.

### 🟡 The messages page shell is unstyled

**File:** `frontend/src/features/messages/MessagesPage.jsx` uses `.chat-shell`, `.chat-header`, `.chat-body`, `.chat-input`, `.chat-title`, `.chat-back`, `.chat-empty`, `.chat-banner`, `.chat-skeletons`, `.sk-bubble` — **none of which have any CSS.** The message *bubbles* (in `Conversation.jsx`) are themed correctly, but they sit in a raw, unstyled wrapper. This is why the messages page looks unfinished.

**The fix.** Add themed styles for those `.chat-*` classes to `_messages.scss` (mirror the existing `.messages-*` / `.admin-*` patterns already in that file — same variables, same structure). This is purely additive; it won't touch anything that works. Ask me for a ready-to-paste block when you want it.

### 🟢 Inconsistent class-naming conventions

You have parallel naming schemes for the same area — e.g. messages uses both `.messages-*` (styled) and `.chat-*` (unstyled), and buttons appear as both `.button`/`.button--primary` (themed system) and bare `.btn`/`.btn-delete` (ad-hoc). Not a bug, but it's why styling slips through the cracks. **Longer-term:** pick one convention per concern and migrate toward it. No urgency; note it for when you next touch these files.
